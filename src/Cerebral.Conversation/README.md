# Pegasus Conversation harness

This source tree contains native module `pegasus.conversation` 1.0.12. Runtime package and saved workflow-definition selection are separately qualified by the owner; this source version alone does not activate a definition. The legacy pure harness remains `pegasus.conversation:chat` 1.0.1. The opt-in `1.0.7-repeat-prepared.1` definition combines the current-generation repeat-build guard with the exact prepared-effect rejection contract. The exported `1.0.6-repeat-guard.1` and `1.0.4-prepared-intervention.1` definitions retain their prior separate policies and cannot be retroactively changed for accepted runs. A prepared rejection retires only a never-dispatched intent and steers a new planning step; a distinct later effect can receive one reviewed permit without resetting the accepted failure count. The shared `ConversationWorkflowContract` is the single identity source used by the harness, Worker, and desktop clients. The host composition root wraps it with `AgentWorkflowDefinition` and binds `cerebral.host` 1.2.0. This package owns no scheduler, database, HTTP client, model runtime, or direct process execution. The opt-in `1.0.8-owner-verified-prepared.1` definition additionally requires a successful Worker-admitted owner checker receipt for the current source generation and canonical build before `plugin.verify`, `plugin.present`, or final completion. Its checker recipe comes only from the frozen submission settings; a successful build command or an ordinary `process.run` receipt does not satisfy the requirement. A later source mutation, rebuild, or unconfirmed process operation clears that credit.

The `1.0.8-owner-verified-prepared.1` reader requires Worker snapshot edition 8, which freezes the chat permission binding and optional owner checker recipe together. Retained edition 6 ordinary and edition 7 owner-only snapshots remain parseable under their original contracts and cannot acquire edition 8 chat authority. Reading a retained snapshot does not authorize replay under the new definition; its edition 8 reader refuses an older settings record before effects. Historical definitions keep their own versioned readers and Worker admission checks.

Input is an object with optional absolute `workingDirectory`, opaque `projectId` metadata, `responseSharePercent` 5–50, and up to eight distinct exact `requiredSuccessfulTools`. Neither a project identifier nor a directory expands tool authority. A required tool name does not grant or discover that tool; it only prevents a generated final action from completing until the current run contains a successful host receipt for that exact name. The host retains exact accepted user text and private plugin assignment independently of display projections.

First effects read the host-frozen earlier conversation snapshot and discover a concise tool catalog. Plain responses require no tool. The model emits one complete JSON action: `final` with text, `blocked` with reason, `describe` with 1–8 exact tool names, `tool` with name/arguments, `questions` with 1–8 fields, `receipt` with current-run effect ID/offset, or `history` with an older cursor or exact historical event ID/offset. Only a complete Stop generation can dispatch an action. General action correction tracks the unresolved failure identity: at most two corrections for the same failure and eight overall without a complete action. Specific admission, replay and completion guards retain their own bounds. An already accepted action, a corrected request and an unchanged failed request are distinct; no correction allowance authorizes repeating an uncertain effect.

Exact schema selection replaces the prior set. Generation passes an empty toolNames array to avoid reinjecting all host schemas. Catalog discovery is reference data; host execution still revalidates accepted/current grants, schemas, paths, cancellation and failed execution budgets. The final result is `{summary,toolReceipts}`: generated user-facing prose and recorded execution outcomes are distinct.

History pages and exact historical reads remain bound to the accepted conversation snapshot. Older pages are prepended chronologically. Historical lookup still allows eight pages of at most 4096 UTF-8 bytes. The qualified 1.0.9 receipt reader follows confirmed forward cursors and revision-bound uncertain receipts, with up to 64 recognizable receipt proposals and 512 KiB of admitted requested data windows per run. Each admitted receipt window is capped at the host's 16 KiB page limit. Malformed, refused and repeated proposals consume attempts; unrelated tool outcomes do not replenish the run allowance. The byte allowance describes requested data windows, not JSON wire size or model tokens. Pages may be fragments. Exact reads do not rerun commands or grant new success evidence. Hidden human projections remain eligible model context. Typed attachment references remain typed in accepted input and bounded history. The host selects a scoped resource adapter; files and images require that adapter's actual capability and exact attachment lookup. The harness never reads a local path or turns a display label into attachment contents. Oversized required typed history reports an explicit overflow. Current compaction retains non-text reference metadata and does not claim to summarize image pixels.

Typed host context overflow requests the separate compact effect. Candidate source manifest, revision, placement, effect identity and measured improvement must validate before adoption. Compaction replaces only reducible live projections; original events/receipts stay in the host database. Latest tool evidence and latest exact answers remain required. Mixed prior/current summaries retain the host's placement marker. The same unchanged window cannot compact twice. Large tool content is explicitly excerpted with an exact receipt handle; user answers are never silently clipped.

Bounds are explicit: 128 combined live/checkpoint source identities, 128 KiB durable state, 48 KiB host history/catalog receipts, eight selected schemas, sixteen schema selections per turn, and the host workflow step/time limits. These are bounded turns, not unlimited transcript hydration. Oversized required input, invalid checkpoints, unsupported specialized legacy follow-up tools and uncertain effects return actionable failure. The 1.0.9 candidate distinguishes durable UTF-8 state exhaustion from model-token capacity. If a capacity failure itself cannot fit the 128 KiB engine state bound, it commits a terminal omission record capped at 64 KiB, preserving exact run/request/conversation/profile/definition identity, omitted-state bytes/hash and bounded original evidence coordinates. Fitting failure state remains unchanged. The terminal record cannot resume, dispatch work or confer build/success evidence; original host events and receipts remain authoritative.

Deterministic tests live in `tests/Cerebral.Worker.Tests/ConversationHarnessTests.cs`. They simulate host outcomes; they do not establish live model, tool, UI, or deployment success.

## Opt-in workflow progress edition

`ConversationAgentHarness.CreateWorkflowProgressEdition()` selects the immutable definition `pegasus.conversation:chat` `1.0.3-workflow-progress.1`. Its private package uses package version `1.0.3` and the explicit `WorkflowProgressConversationServicePlugin` entry, which exports legacy chat `1.0.1` and this opt-in definition. The default constructor, legacy entry, source manifest, and separate `1.0.2-generic-context.1` entry keep their existing selections. An accepted run still requires its exact definition version and package generation.

This edition builds on generic context contributions. Immediately before an ordinary Generate command is persisted, Conversation derives a pure progress view from declared required-successful-tool obligations, existing generation-bound milestones, latest saved tool receipts, and retained source/reference metadata. A fixed host-authored leading system cue, detailed progress facts in the existing user-role evidence message, and the executable action schema are materialized together in those durable arguments. Opaque provider receipt identifiers and exact reference handles remain user-role reference data. The existing UTF-8 evidence bound is checked after appending the detailed facts; overflow refuses explicitly without truncation. Preparation and full, floor, and compaction-candidate measurements therefore receive the same cue and schema. No provider callback recomputes workflow phase.

Only the existing `MissingSuccessfulTools` predicate controls the action view: while it reports an unsatisfied obligation, the edition removes the direct `final` alternative and preserves every other existing branch and constraint. It keeps discovery, questions, receipt/history reads, blocked replies, tool actions, and delegation when those branches are otherwise legal. Diagnostic failed, Unknown, partial, truncated, or nonzero-exit status does not create an additional completion predicate. Model proposals and a currently dispatched Generate effect are not saved successful tool outcomes. Plain chat with no declared obligations or observed tool receipts receives no added cue or schema restriction.

The detailed reference evidence contains metadata rather than tool bodies, prioritizes required names, and shows at most eight latest tool outcomes, eight retained references, and eight provider receipts. Omitted tool/reference counts remain explicit. Retained references and incomplete sources do not prove arbitrary deliverable completion or recovery of a whole source, and listing a reference does not require a read after every compaction. Persona selection, immutable source/settings text, and provider receipt identity remain owned by their plugins.

Focused private verification inputs live under `build/Core/OwnerQuiescence/ConversationProgress-sample-source`. They exercise pure harness/schema behavior, actual private Registry/SQLite WorkflowStore/provider normalization and package loading, the real Persona resolver, compiled Worker framing, exact generation and active-pin refusal, and PE/PDB source checks. Model/token counts and preparation leases are deterministic test metadata. These checks establish no new model inference, network, installed activation, or production deployment evidence.
