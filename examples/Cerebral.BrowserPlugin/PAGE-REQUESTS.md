# Explicit page source requests

The service plugin declares `browser.request` with the existing `browser.read` capability. It performs GET only through BrowserNetworkGate and uses the caller's host-owned profile, conversation and job scope. The request needs `requestId` and `url`; optional `tabId` must identify that scope's active rendered tab. No request body, method override, headers, cookies, browser state, credentials or proxy is accepted. Page requests do not launch a browser or execute JavaScript.

`maximumBytes` defaults to 65536 and ranges from 1024 to 262144 received bytes. `maximumTextBytes` defaults to 12000 and ranges from 256 to 16384 UTF-8 bytes. Responses support uncompressed text, HTML, JSON and XML source with UTF-8, ASCII or Latin-1; unsupported encodings, authentication challenges and attachments stop retrieval. The result identifies requestId, opaque requestSessionId, optional tabId, statusCode, redacted final URL, contentType/encoding, byte counts, truncation and `contentTrust=untrusted-page-data`. Source text can contain scripts or markup as inert untrusted data. Use browser.open/navigate/inspect for JavaScript-rendered page inspection.

Each redirect is checked before its next connection, with at most five followed redirects. The shared gate pins the DNS result to the connected socket; a second lookup cannot rebind it. DNS names do not implicitly grant numeric local/shared/special-purpose addresses. Explicit numeric profile grants permit intended local requests, while unspecified, multicast, link-local and broadcast addresses remain denied. The conservative special-purpose classification is informed by the [IANA IPv4 registry](https://www.iana.org/assignments/iana-ipv4-special-registry) and [IANA IPv6 registry](https://www.iana.org/assignments/iana-ipv6-special-registry). No website was requested to verify those address classes.

Requests and rendered traffic share session lifetime, pacing, queue limits, a 512-request ceiling and the 64 MiB received-byte ceiling. Idle sessions and browser.close-all release HTTP clients and any browser runtime. Browser.open can attach its existing isolated runtime to an HTTP-only session. The existing rendered open, navigate, inspect, click, fill, screenshot and close actions remain declared.

Reuse requestId only for identical arguments and policy in the same profile/conversation/job. Arguments and policy are hashed in the in-process retry index, so query/fragment data is not retained there or echoed by error/URL projections. Host effect IDs cannot be substituted through another request ID. A dispatched cancellation, timeout or incomplete/denied response records Unknown and the same request is never resent within that provider lifetime.

The retry index has at most 256 non-evicting attempt markers; capacity exhaustion rejects new work before dispatch. Each marker is bounded to 8 KiB UTF-8. Additional serialized response-body retention is charged against a separate 2 MiB aggregate budget, making retained result content at most 4 MiB UTF-8, excluding bounded index keys and ordinary object overhead. UTF-16 storage can use up to twice that content amount. Each full public response is bounded to 128 KiB serialized UTF-8. A response may reach its first caller with `receiptBodyRetained=false`; later retries return the completed metadata with `bodyAvailable=false` and no text, without another GET. A fresh read then needs a new explicitly selected request ID. Unknown markers remain intact.

These indexes are ephemeral and are lost on provider disposal/reload or process restart. They are not a durable mutation receipt and cannot guarantee retry safety across those boundaries. Host durable effects and their reconciliation remain authoritative; never automatically retry an unknown request after reconnecting to another provider generation.

The package is a cross-platform service plugin. An owner control can use the existing `tools.call` route with a selected profileId, `sessionId=direct` or a stored owned legacy conversation, name `browser.request` and bounded arguments. The current owner route rejects native/Cortex conversation IDs; it does not provide a native Main browser-control bridge. Do not fabricate a conversation binding or treat direct scope as current-native-conversation acceptance. Engine-dispatched browser tools still require the genuine host-owned ToolExecutionContext. The Worker selects/grants the actual profile and verifies supported conversation ownership. There is no raw browser.request service command that accepts profile authority from caller arguments. A WPF mount requires a separate agreed owner seam; this change does not add one.

Focused verification uses isolated task-private loopback HTTP fixtures and existing deterministic policy/resource checks. Rendered Playwright acceptance is separate and requires an existing permitted cached runtime; no browser is installed or activated by these checks.
